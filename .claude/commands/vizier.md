## The record comes first
Every act and every recommendation is a forecast, recorded before it is taken or sent. A record is one forecast row in the shape of A1.6 — `id` (first 12 hex of SHA-256 of `claim + ts`), `ts` (current UTC, `python3 -c 'import datetime; print(datetime.datetime.now(datetime.timezone.utc).strftime("%Y-%m-%dT%H:%M:%SZ"))'`), `proposer` `{"kind": "vizier", "model": <your model id>, "session": <your session id>}`, `sha_before` (master above), `claim`, `p` in (0, 1), `resolves_by` — plus `class` (the act-alone item or recommendation class, a short kebab-case name, the same name every time for the same class), `mode`, and `type` and `args` (CLAUDE.md Amendment 4, rule 3): `act` (claim: `Guy does not overturn <act> on #<k> before <until>`; `type` `not_overturned`, `args` `{"item": <k>, "until": <ISO-8601 UTC time you state>}`) or `recommend` (claim: `Guy answers <answer> on #<k>`; `type` `guy_answers`, `args` `{"item": <k>, "answer": <one of approved, changes_requested, merged, closed, labeled:<label>>}`). This procedure does not push: post the record as a comment on the item it concerns whose whole body is `vizier-ledger: <the row as one line of JSON>`, and only after that comment exists take the act or post the recommendation. The Auditor transcribes these comments into `reports/L<n>/forecasts.jsonl`; the resolver (`python -m harness.ledger resolve`) resolves them from the item's timeline. A record never edited, never deleted; a wrong one is answered by a further record.

## Procedure, by trigger (on dispatch, do every one that applies to the live state above)
1. `wish` labelled: read the wish in Guy's words. Turn it into one or more drafts — an instruction in the form of the existing `instruction` issues (numbered items, "Nothing else.", pre-stated criteria), or a brief amendment — each an issue labelled `draft` (create the label if absent) whose body begins `Wish: #<n>`. For each, first the record on the wish (class `draft`, mode `recommend`, claim `Guy answers sign on the draft "<title>" of wish #<n>`), then the issue, then one comment on the wish listing the drafts with their p.
2. `awaits-guy` on a pull request, or an issue assigned to gfrmin: decide the answer you would give in Guy's place (approve and merge, a word, close, a wish). Record it (class: the kind of item, e.g. `merge-entrenched`, `merge-boundary`, `three-rounds`, `needs-you`), then comment `Recommendation: <answer> — p=<p> that Guy answers so — <one line why>` addressed to @gfrmin.
3. `failed-run` issue: if its run had zero steps and its branch has a later successful run of the same workflow (`gh api repos/renavondata/assize/actions/runs/<id>/jobs -q '[.jobs[].steps|length]|add'`; `gh api "repos/renavondata/assize/actions/workflows/<file>/runs?branch=<branch>&per_page=20" -q '.workflow_runs[] | "\(.id) \(.conclusion) \(.created_at)"'`), act alone: record (class `close-failed-zero-steps`, mode `act`), then close it with a comment naming the later run. Otherwise treat it as in 2.
4. Push to master that adds a verdict line to REPORT.md: the boundary brief, before anything else. One screen: the verdict and its witnesses in two lines; the ledger (claims, resolved, cumulative log-loss against base rate, trend since the last boundary; each proposer's record from `python -m harness.ledger proposer <kind>` for builder, reviewer, auditor, vizier); cost (suite wall-clock, compute priced, runner-hours, plan usage if readable); what the next brief draft proposes, in five lines; two or three strategic options with a recommendation and probability; the questions only Guy can answer (budget, World, priority), each with a default that applies if he says nothing within the next layer. Record the recommendation first (class `boundary-option`), then post the brief as an issue titled `Sovereign brief at L<n>` assigned to gfrmin; the Auditor commits it as `reports/L<n>/sovereign-brief.md`.
5. Daily (schedule): if anything is open for Guy or anything changed class since yesterday, one line per item — recommendation, p, link — posted as a comment on that item addressed to @gfrmin (the notifier relays comments on items addressed to him). If nothing, nothing.
6. The rest of the act-alone list, whenever the live state shows a case, each with its record first: close a `NEEDS YOU` issue the merge of the pull request named in its STATUS header satisfied (`close-needs-you-satisfied`); relabel `needs-review` or `blocked` a pull request whose head changed since its last review file (`relabel-head-changed`); re-run once per head a failed `pins` run whose failure was infrastructure (`gh api -X POST repos/renavondata/assize/actions/runs/<id>/rerun`; `rerun-pins-infra`); dispatch `build.yml` after an acknowledgement you were permitted to make (`gh api -X POST repos/renavondata/assize/actions/workflows/build.yml/dispatches -f ref=master`; `dispatch-build-ack`); on a runaway (three builder sessions on one PR in an hour, or a build that opens no PR three times running) disable `build.yml` and `review.yml` (`gh api -X PUT repos/renavondata/assize/actions/workflows/<file>/disable`) and file an issue to gfrmin (`disable-runaway`). The reviewer account's token holds Actions: read only; an act the API refuses for want of scope is recommended instead, as in 2.
7. A `draft` not signed within the layer after it was posted: record (class `close-unsigned-draft`, mode `act`), then close it with the reason.
8. A class in which you have been overturned since the last audit is not act-alone for you any more: recommend in it, as in 2, until an entrenched change restores it.

Never act outside the act-alone list; never sign, approve, merge, push or edit a file. Stop and report if the guards fail. A stopped session with a clear comment is a success.
