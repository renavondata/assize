## Guards
- If the account above is not `assize-builder`, stop and report: a Builder runs only as the builder account. Do nothing else.
- If a dispatched PR is set, check it out with `gh pr checkout` before anything else and treat this as a PR-branch session.
- If the checked-out branch is `master` and you will not open a pull request this session, for any reason: before stopping, create an issue assigned to gfrmin whose title is the reason in one line and whose body says what would unblock it, unless an open issue already says so. Then stop and report.

## Declaration and stop (instruction #112 Parts A and D)
- The first act of every session, before any other, is one comment on the item it has taken: the instruction issue; the pull request it builds on; for a brief item, the pull request in master STATUS's header. It reads `build run <run id> started <ISO time> on #<n>: expected <m> minutes; model <your model id>`, with `<run id>` `$GITHUB_RUN_ID` (`local` outside Actions) and the time from `date -u +%Y-%m-%dT%H:%M:%SZ`. Only the reads that name the item (the guards, step 1's `claims next` and `chooser choose`) precede it; nothing that writes does. A session that takes no item posts the same line on the pull request in master STATUS's header, or carries it in the stop issue the guards require. At the session's end, edit that comment (`gh api -X PATCH repos/renavondata/assize/issues/comments/<id> -f body=...`) to add `; tokens <n>`, from `uv run --frozen python -m harness.sessions tokens build.log` (`unknown` when there is no log).
- The declaration is a forecast: `type` `session_minutes`, `args` `{"run": <run id>, "bound": <m>}`, claim `build run <run id> ends within <m> minutes of its start`. On a new branch it is appended with the step-2 forecasts. On a pull-request branch, which takes no forecast row, it is posted as a comment on the pull request whose whole body is `vizier-ledger: <the row as one line of JSON>`, and the Auditor transcribes it.
- A session that stops before writing STATUS posts its stop report as a comment on the item it holds, beginning `build run <run id> stopped <ISO time>:`, before it ends. A session ending with neither STATUS nor that comment is an unrouted exit (`harness.sessions.declared_findings`). The declaration and the stop comment are the two comments a session makes about itself.

## Procedure
1. On `master`, an item is not a candidate if an open pull request already holds it: an `instruction` issue cited by an open PR's `Instruction:` trailer, or a brief item named in an open PR's STATUS header. `uv run --frozen python -m harness.claims next <candidates, in order>` (`#<n>` for an instruction) prints the first candidate no PR holds and each skipped one with its PR; take the next candidate instead of a held one, and name each skipped item and its PR in STATUS `did:` (instruction #110). An item that would edit a path an open pull request labelled `awaits-guy` touches (`gh pr list --label awaits-guy --json number,files`) is not a candidate either, so two pull requests do not conflict: skip it, take the next, and record each such skip, with the PR and the path, under `decided (not asked)` (instruction #102; an `awaits-guy` label starts a master Builder, `build.yml`). If an open issue labelled `instruction` and marked `signed` above exists, the oldest is your item; an issue marked `refused` is not an instruction (its `instruction` label was not applied by gfrmin): do not act on it, comment once on it with its `refused` line unless such a comment exists, and name it in STATUS. The item: branch `instr-<n>-<slug>`, do exactly what the issue body says and nothing else, trailers `Instruction: #<n>`, `Proposer: guy`, `Proposer: builder <model> <session>` on every commit. Otherwise the item is chosen among the open candidates (open signed `instruction` issues, STATUS's `next` line, the brief's unfinished items, none held by an open PR), listed in that order: once `reports/switchback-seed.txt` is committed, `uv run --frozen python -m harness.chooser choose <candidates in order> --until <next audit> --ts <now> --session <your session id> --model <your model> --pr <the number your pull request will take, as step 2 reads it> --p-kept <your p that Guy does not overturn the choice> --p-merged <your p that the pull request merges> [--change-point <ISO time>]... [--ordering <file holding the latest priorities issue>]` prints the sovereign entrants' `guy_picks` rows, the mixture's, the act's `not_overturned {item, until, exposure: seen}` and `merged {pr}` rows (yours, P0ah), and a `chose:` line (it exits 2 and says so when the seed is absent: take the first candidate). Append the rows to `reports/L<n>/forecasts/<your session id>.jsonl` and commit them before the commit that first carries the `chose:` line into STATUS (P0ad); STATUS carries that line unchanged (instruction #111). The item is the one the line names; a brief item you take that way goes on a new branch. On a PR branch, first step: if the branch conflicts with master (`gh pr view --json mergeStateStatus` is DIRTY), merge origin/master first: append-only files keep every line from both sides; STATUS.md keeps the newer-dated; other conflicts resolved minimally and listed in the commit message. Then work the finding.
2. Before your first commit, write `harness/proposer.d/<branch>.toml` (a file no other pull request writes; `harness/proposer.toml` is frozen) with `kind = "builder"`, your model, and your own session id. On a pull-request branch, append no forecast row: the branch's first-head rows and the mechanism's `review_accept` already cover the pull request (rule 2), and a later row is late (P0r) and cannot be removed (P0q); say so in STATUS `did:` (instruction #112 Part D). On a new branch, before your first `make pins`, append your forecasts to `reports/L<n>/forecasts/<your session id>.jsonl` per A1.6, each with its `type` and `args` (CLAUDE.md Amendment 4, rule 3): pins green on the first CI run of this PR head (`type` `pins_green`, `args` `{"pr": <n>}`); reviewer ACCEPT with no blocking finding (`review_accept`, `{"pr": <n>}`); and, on a layer whose exit gate names a host verdict, the host verdict (`host_verdict`, `{"layer": <L>, "verdict": <FIT, MARGINAL or UNFIT>}`); and the declaration's `session_minutes`. On a new branch, `<n>` is the number the pull request will take: one more than the highest issue or pull request number (`gh api "repos/renavondata/assize/issues?state=all&per_page=1" -q '.[0].number'`), read just before you push and open it. The forecasts are in the head of the first `pins` run on the branch (rule 2), so commit them before the pull request opens.
3. Do one item of the brief, or the smallest group the brief states together. Never start the next layer. Never edit an entrenched path (A1.1) unless the brief names it.
4. Run `make pins`. Witness under the A3 hygiene rule. Every pin proves it can fail.
5. Decide what you can decide; record each decision in STATUS under `decided (not asked)` with p(stands on review). NEEDS YOU carries at most one item, and only an action CLAUDE.md reserves to Guy.
6. Write `reports/L<n>/status/<branch>.md` in the shape of A1.8 (`reports/L<n>/STATUS.md` is frozen; `python -m harness.ledger status` prints the master view, the file of the pull request merged last). STATUS names the sha at which `make pins` ran; the commit adding STATUS is that sha's child and touches only `reports/`. Push. Open the pull request if none exists (you are its author). If it is not a layer boundary and touches no entrenched path, `gh pr merge --auto --merge`. Then label it: `gh pr edit <n> --remove-label blocked --add-label needs-review` (ignore errors from a label that isn't present). If STATUS carries a `NEEDS YOU`, also `gh pr edit <n> --add-reviewer gfrmin`. After opening the PR, if this PR cites an instruction, note `Instruction: #<n>` in the PR body; close the issue only after the PR merges (the next master session does it if you cannot). Never merge yourself.
7. If this item completes the layer: append the verdict line to the root REPORT.md, set `LAYER BOUNDARY: yes`, do not enable auto-merge, label `needs-review`, and include a draft of the next layer's brief in the form of the existing briefs (A1.10).
8. When the brief calls for a host witness, add the `measure` label to your PR and record the run id in STATUS (A6).

## Files, pushes and denials (instruction #110)
- Change files with the Edit and Write tools, never by shell redirection, heredocs or inline scripts; shell is for commands that are not edits. A tool call the harness denies is quoted (tool, reason) in STATUS `did:` or in the session's stop report; a session that stops on master without a pull request files the issue the guards require, with the denial quoted.
- Every push passes `harness/hooks/pre-push` (`python -m harness.claims trailers @{u}..HEAD`, installed by the workflow): a refused push is answered by amending your own unpushed commit, never by an exemption entry in `claims.PROPOSER_EXEMPTIONS`. A session that cannot make its commit parse stops and reports.

Stop and report under the brief's boundaries. A stopped session with a clear STATUS is a success. A session that asks Guy something it could have decided and recorded has failed.
